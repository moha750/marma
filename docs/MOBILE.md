# تطبيقا أبل وقوقل — البنية والنشر

مَرمى يُنشَر من **مستودعٍ واحد** بثلاث نسخ: موقع الويب، وتطبيق iOS، وتطبيق أندرويد.
الثلاثة تشترك في كل الكود — ما يختلف هو الحزمة والقشرة الأصلية.

---

## لماذا Capacitor ولا إعادة كتابة؟

مَرمى نظامٌ يعمل في الإنتاج بعشرات الشاشات ومنطقِ أعمالٍ ناضج. إعادة كتابته بـ
React Native أو Flutter تعني أشهراً من العمل ونسختين من كل ميزةٍ بعد ذلك للأبد.
Capacitor يضع الكود نفسه داخل قوقعةٍ أصلية ويمنحه واجهات النظام (إشعارات،
كاميرا، اهتزاز، محفظة) — فتبقى الميزة تُكتب مرّةً واحدة وتظهر في الثلاثة.

الثمن المعروف: أبل ترفض «موقعاً في قوقعة» (القاعدة 4.2). لذلك التطبيق يحمل قيمةً
أصلية حقيقية: إشعارات النظام، ماسح كاميرا، مناطق آمنة، زر رجوع أصلي، وعملٌ بلا
شبكة — لا مجرّد عرضٍ لصفحة.

## الفروق بين نسخة الويب ونسخة التطبيق

| | الويب | التطبيق (iOS/Android) |
|---|---|---|
| نقطة الدخول | `index.html` (تسويق) | `app.html` ← تُخرَج باسم `index.html` |
| المكتبات | من `/assets/vendor` | نفسها، **داخل الحزمة** |
| Service Worker | يعمل | معطَّل (الأصول من الحزمة لا الشبكة) |
| صفحة التسويق والأسعار | موجودة | **مُستبعدة** (قاعدة أبل 3.1.1) |
| لوحة المشرف العام | `/admin/*` | مُستبعدة |
| صفحتا الحجز والبطاقة العامّتان | موجودتان | مُستبعدتان (تُفتحان في متصفّح النظام) |
| طلب اشتراك / آيبان / سعر | موجود | **مُخفى بالكامل** |
| تسجيل دخول قوقل/أبل | تحويل عادي | متصفّح النظام + رابط عودة مخصّص |
| مجلد البناء | `dist/` | `dist-native/` |

كل هذه الفروق يُنفّذها هدف بناءٍ واحد: `MARMA_TARGET=native` في
[vite.config.js](../vite.config.js). لا نسخة ثانية من أي ملف HTML — قوقعة التطبيق
**تُولَّد** من `app.html` كي لا تتباعد النسختان عند إضافة سكربت جديد.

## الأوامر

```bash
npm run dev                  # تطوير الويب كالمعتاد
npm run build                # نسخة الويب → dist/

npm run build:native         # حزمة التطبيق → dist-native/ + مزامنة المنصّتين
npm run ios                  # بناء + تشغيل على محاكي أبل
npm run android              # بناء + تشغيل على محاكي أندرويد
npm run ios:open             # يفتح Xcode (للتوقيع والرفع)
npm run android:open         # يفتح Android Studio
```

> **أندرويد محلياً** يحتاج JDK 21 + Android SDK (عبر Android Studio). ولو لم
> تُركّبهما فلا مشكلة: مسار GitHub Actions يبني أندرويد عند كل دفعة ويعطيك APK
> جاهزاً للتجربة — انظر [.github/workflows/mobile.yml](../.github/workflows/mobile.yml).

## ما يجب أن تعرفه قبل أي تعديل

### ١) المسارات داخل التطبيق
Capacitor يخدم `index.html` لأي مسارٍ **بلا امتداد**. نتيجتها:

- مسارات الراوتر (`/dashboard`, `/customers/:id`) تعمل تلقائياً ✅
- مسارات المستندات الحقيقية (`/auth/login`) كانت ستفتح قوقعة التطبيق ❌

الحلّ في مكانين: إعادة كتابة `href` وقت البناء، ودالة `window.native.docPath()`
التي تمرّ عليها كل ملاحة برمجية (مصبّها الوحيد `withBase` في
[src/core/auth.js](../src/core/auth.js)).

**لذلك:** أي صفحة HTML جديدة خارج الـ SPA يجب أن تُضاف إلى `input` في
`vite.config.js`، وأي رابطٍ إليها يمرّ على `window.native.docPath()`.

### ٢) أنماط التطبيق محصورة
كل أنماط البيئة الأصلية في [styles/components/native.css](../styles/components/native.css)
تحت `html.native` حصراً. الويب في الإنتاج لا يراها — فالتعديل هناك آمن.

### ٣) لا CDN أبداً
مكتبات الطرف الثالث تُنسخ من `node_modules` إلى `assets/vendor` عبر
[scripts/sync-vendor.mjs](../scripts/sync-vendor.mjs). أبل تمنع تنزيل كودٍ تنفيذي
وقت التشغيل (2.5.2)، والـ CI يفشل إن تسرّب رابط CDN إلى الحزمة.

لترقية مكتبة: `npm i <pkg>@<version> --save-exact` ثم `npm run vendor`. لو نقلت
الحزمة ملفاتها الداخلية، السكربت **يوقف البناء** بخطأٍ صريح بدل أن يَنشر تطبيقاً
بلا أيقونات.

### ٤) الأسعار ووسائل الدفع ممنوعة داخل التطبيق
قاعدة أبل 3.1.1: كل خدمةٍ رقمية تُباع داخل التطبيق تمرّ بمشتريات أبل. عرض آيبان
لتحويل قيمة الاشتراك = وسيلة دفعٍ خارجية = رفض. أي نصٍّ جديد فيه سعر أو دعوةٌ
للشراء يجب أن يُحاط بـ `if (window.native && window.native.isNative)`.

## إعدادٌ لمرّة واحدة (ما يحتاج حسابك)

### أبل
1. **App Store Connect** → تطبيق جديد، Bundle ID: `help.marma.app`
2. **Certificates, Identifiers & Profiles** → في الـ App ID فعّل:
   `Push Notifications` و `Sign in with Apple` و `Associated Domains`
3. **مفتاح APNs** (`.p8`) للإشعارات — واحدٌ يكفي للتطبيق كله
4. **مفتاح App Store Connect API** (`.p8`) لرفع النسخ آلياً من CI
5. في Xcode: `Signing & Capabilities` → فريقك + إضافة
   `Push Notifications` و `Sign in with Apple`

### قوقل
1. **Play Console** → تطبيق جديد، package: `help.marma.app`
2. **مشروع Firebase** (لازم للإشعارات على أندرويد فقط) → نزّل
   `google-services.json` إلى `android/app/`
3. **مفتاح توقيع** (keystore) + تفعيل Play App Signing
4. **حساب خدمة** لرفع النسخ آلياً من CI

### Supabase
أضِف رابط العودة المخصّص إلى قائمة الروابط المسموحة:
**Authentication → URL Configuration → Redirect URLs**

```
help.marma.app://auth/callback
```

بدونه يفشل تسجيل الدخول بقوقل وأبل داخل التطبيق برسالة `redirect_uri` غير مسموح.

## الإشعارات الأصلية

Web Push لا يعمل داخل قوقعة التطبيق: `WKWebView` على iOS لا يملك Push API، و
`WebView` على أندرويد كذلك. فالتطبيق يستخدم قناتين أصليتين، والويب يبقى على
Web Push كما هو. الثلاث قنوات تُرسَل من نفس الدالة بنفس النصّ.

| المنصّة | القناة | الحمولة |
|---|---|---|
| الويب | Web Push (VAPID) | كما كانت |
| أبل | APNs مباشرةً | `apns-topic` = `help.marma.app` |
| أندرويد | FCM HTTP v1 | `ic_stat_notify` + صبغة خضراء |

### نقطتان تستحقّان معرفتهما

**١) مفتاح APNs عندك أصلاً.** مفتاح الإشعارات في حساب أبل مربوط بالفريق لا
بتطبيقٍ واحد، ومَرمى تستخدمه اليوم لتحديث بطاقات المحفظة. فالتطبيق يستخدم المفتاح
نفسه — يتغيّر الموضوع (`apns-topic`) فقط. **لا مفتاح جديد ولا سرّ جديد لأبل.**
الكود مشترك في `supabase/functions/_shared/apns.ts` (استُخرج من `wallet-sync`
حيث كان يعمل في الإنتاج، فلا نسختان من توقيع ES256 تتباعدان).

**٢) أندرويد وحده يحتاج Firebase.** لا مفرّ: أندرويد لا يقبل إشعاراً إلا عبر FCM.
والسرّ المطلوب واحد:

```bash
supabase secrets set FCM_SERVICE_ACCOUNT="$(cat ~/Downloads/marma-firebase-adminsdk.json)"
```

> من Firebase Console → Project settings → Service accounts → Generate new private key.
> ونستخدم HTTP v1 لا `server key` القديم: أوقفته قوقل، وأي كود يعتمده يعمل
> حتى تُغلق البوابة ثم يصمت بلا تفسير.

وتنزيل `google-services.json` إلى `android/app/` (لا يُلتزم في git).

### إن صمتت الإشعارات
الاستجابة تُرجع تفصيلاً بالمنصّة يقول أي قناةٍ صمتت:
```json
{ "sent": 3, "failed": 1, "byPlatform": { "web": 2, "ios": 1, "android": 0 } }
```
`android: 0` مع وجود أجهزة = `FCM_SERVICE_ACCOUNT` غير مضبوط (والسجلّ يقولها).

**فخّ iOS الشهير:** `aps-environment` في `App.entitlements` قيمته `development`
محليّاً، وأداة الأرشفة تستبدلها بـ `production`. فنسخة Debug على جهازك تُسجَّل على
sandbox، وإرسالٌ إلى مضيف الإنتاج لا يصلها. للاختبار على جهاز تطوير:
```bash
supabase secrets set APNS_HOST="https://api.sandbox.push.apple.com"
```
وأعِدها لمضيف الإنتاج قبل النشر (أو احذف السرّ فيرجع للافتراضي).

## الروابط العامة (Universal Links / App Links)

رابط `marma.help/bookings` يفتح التطبيق مباشرةً بلا مرور بالمتصفّح.

الملفّان في `public/.well-known/` ويُنشَران مع الموقع تلقائياً:
`apple-app-site-association` و `assetlinks.json`. و`_headers` يضبط لهما
`Content-Type: application/json` — بلا نوع JSON ترفض أبل الملفّ **صامتةً** فتفتح
الروابط في المتصفّح ولا يظهر أي خطأ يدلّك على السبب.

**ما يُستثنى عمداً:** `/book` و `/card` (صفحتا العميل — من يفتحهما لا يملك
التطبيق، واستيلاء التطبيق عليهما يعني رابط حجزٍ ترسله لعميلٍ ثم يفتح في تطبيقك)،
و`/auth/*` (روابط استعادة كلمة المرور تحمل رموزها في الرابط).

### خطوة تبقى عليك
بصمة توقيع أندرويد لا تُعرَف إلا بعد إنشاء التطبيق في Play Console. خُذها من:

**Play Console → Setup → App integrity → App signing key certificate → SHA-256**

وضعها في `public/.well-known/assetlinks.json` بدل
`REPLACE_WITH_PLAY_APP_SIGNING_SHA256`. فحص CI يُنبّهك (تحذيراً لا فشلاً) ما دامت
بديلاً — وإلى أن تُضبَط تفتح روابط `marma.help` في المتصفّح على أندرويد فقط،
وكل شيء آخر يعمل.

للتحقّق بعد النشر:
```bash
curl -sI https://marma.help/.well-known/apple-app-site-association | grep -i content-type
# يجب أن يقول: application/json
```

## ⚠️ قائمة ما قبل الإطلاق

أشياء صحيحةٌ الآن للاختبار، وخاطئةٌ في الإنتاج. راجعها قبل رفع أول نسخة للمتجر:

| # | الإجراء | لماذا |
|---|---|---|
| ١ | `supabase secrets unset APNS_HOST --project-ref vwzseueqfghirhyhwbva` | ضُبط على sandbox لاختبار نسخة التطوير. نسخة المتجر تُسجَّل على **الإنتاج**، والإرسال إلى sandbox **لا يصلها** — بلا خطأ ولا سجلّ |
| ٢ | بصمة SHA-256 في `public/.well-known/assetlinks.json` | من Play Console. بدونها تفتح روابط `marma.help` في المتصفّح على أندرويد |
| ٣ | `FCM_SERVICE_ACCOUNT` + `google-services.json` | بدونهما لا تصل إشعارات أندرويد إطلاقاً |
| ٤ | حساب تجريبي فعّال لمراجع أبل | أكثر ما يعطّل أول إصدار — لا الكود |

> **درسٌ من الاختبار الحقيقي:** أي دالة يناديها التريجر يجب أن تكون معلنة في
> `supabase/config.toml` بـ `verify_jwt = false`. ضبطها من لوحة التحكم لا يكفي:
> أوّل `functions deploy` (ومنه النشر الآلي) يُعيدها للافتراضي فتصمت الدالة تماماً
> — بلا خطأ في سجلّها، لأنها لا تعمل أصلاً. حدث هذا فعلاً مع `send-booking-push`
> وثلاث دوال أخرى، واكتُشف من `net._http_response` لا من سجلّ الدوال.
